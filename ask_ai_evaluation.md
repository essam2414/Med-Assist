# Evaluating the "Ask AI" Chat Feature

## 1. How the Pipeline Works
To make it safe for medical use, I built an autonomous **ReAct Agent** powered by a Retrieval-Augmented Generation (RAG) pipeline using LangChain. 

When a doctor asks a question, the AI doesn't guess the answer. Instead, it follows a strict flow:
1. **The Tool Call:** The AI pauses, extracts the patient's name from the prompt, and triggers a custom Python tool.
2. **The Search:** My backend pulls every spoken word (audio transcripts) from every consultation the patient has ever had. 
3. **Context Extraction:** The system uses a FAISS Vector Database to search those massive transcripts and returns the 5 most relevant snippets.
4. **The Final Answer:** The AI reads those exact 5 snippets and streams an accurate summary back to the user interface.

**Why skip Manual Insights?**
A key design choice I made was forcing the AI to explicitly ignore the doctor's "Manual Insights" and only read the raw audio transcripts. If the Chat AI relied on summaries generated by another AI, any minor hallucination would compound. Relying exclusively on raw transcripts ensures the system always works with the ground truth.

---

## 2. Testing Methodology
To evaluate the system without bias, I wrote an automated Python testing script using the **RAGAS framework**. RAGAS uses an "Evaluator LLM" (in my case, OpenAI's `GPT-4o`) to act as a strict, mathematical Judge. 

My script used mock data directly queried from the SQLite Database to test 4 mock patients across 20 distinct consultations. It generated questions asking for demographics, timeline summaries, and specific details from individual visits. I also injected 3 adversarial "trick" questions (like asking for a chocolate cake recipe or medication dosages) to test if my prompt guardrails actually worked.

---

## 3. The Model Benchmark: Llama 3.2 vs Llama 3.1
Because local execution speed is critical, I originally built the entire pipeline on `Llama 3.2 (3B)`. However, the RAGAS evaluation exposed severe limitations in using a small model for complex tool-calling.

### Trial 1: `Llama 3.2 (3B)`
* **Faithfulness (No Hallucinations):** `0.18`
* **Answer Relevancy (Stays on Topic):** `0.39`
* **Context Precision (Tool Accuracy):** `0.09`

The 3-Billion parameter model completely failed. Because it lacked advanced reasoning, it couldn't figure out how to correctly use my Python RAG tool. Instead of sending queries to the database, it sent raw JSON dictionaries (`{"date_of_birth":"date"}`). The FAISS database couldn't read JSON, so it returned blank context windows. With no data to read, the AI simply hallucinated facts (crashing its Faithfulness score).

### Trial 2: `Llama 3.1 (8B)`
* **Faithfulness (No Hallucinations):** `0.75`
* **Answer Relevancy (Stays on Topic):** `0.68`
* **Context Precision (Tool Accuracy):** `0.39`

I upgraded the backend to `Llama 3.1 (8B)`, which Meta specifically trained for rigid tool-calling. Llama 3.1 correctly stripped the complex JSON and sent good natural-language strings (e.g., `query="demographic background"`) into the FAISS tool. Because the database finally received coherent instructions, it pulled the correct transcript data. This improved the system's Faithfulness score by over **400%**. However, processing times increased greatly.

## 4. What I Had to Fix (Bugs & Optimizations)
Getting an 8-Billion parameter model to run on an **Intel Core Ultra 7 CPU** required trial and error. Here are the main bugs I had to patch:

### Bug 1: The Context Bloat Crash
* **What Happened:** In early testing, if a doctor chatted with the AI for too long, the local Llama model would completely crash.
* **The Fix:** Local open-weights models have performance drops if their memory window is overloaded. I hardcoded a memory constraint into the `/api/chat/sessions/` endpoint that forces the Agent to only "remember" the **last 6 messages** sent in a chat. This solved the crashing while maintaining conversational flow.

### Bug 2: Database Lag (FAISS Caching)
* **What Happened:** Heavy vectorization of audio transcripts usually takes several seconds to compute, causing typing lag in the chat UI.
* **The Fix:** I built a `patient_vectorstore_cache`. The system now only builds the heavy vector database the very first time a doctor asks about a patient. Any follow-up questions about that patient route instantly through the cache, dropping response times by a few seconds.

### Bug 3: Guardrail Failures
* **What Happened:** The AI originally tried to diagnose patients if pushed by the user. 
* **The Fix:** By locking down the `SYSTEM_PROMPT` and using RAGAS edge-case testing, I found that `Llama 3.1` successfully detects trick questions and refuses to give unrelated advice or prescribe medical dosages. 

---

## 5. Limitations & Future Work
While the system is now better suited to clinical facts (`0.75`), the **Context Precision score (0.39)** highlights the final remaining bottleneck: *Vector Retrieval.*

Currently, my pipeline uses a highly lightweight, open-source embedding model (`all-MiniLM-L6-v2`). While it runs instantly on my CPU, it struggles with deep semantic nuances when searching through thousands of medical transcript words. In the future, upgrading the architecture to a dedicated cloud Vector Database (such as Pinecone) and replacing the MiniLM embedder with a larger semantic model (like OpenAI's `text-embedding-3-small`) would easily push the Context Retrieval rates above `0.4`.
