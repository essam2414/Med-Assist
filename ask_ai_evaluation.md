# Evaluating the "Ask AI" Chat Module

## 1. How the Pipeline Works
Building the "Ask AI" feature wasn’t as simple as plugging in a standard chatbot. To make it safe for medical use, I built it as an autonomous **ReAct Agent** powered by a Retrieval-Augmented Generation (RAG) pipeline. 

When a doctor asks a question, the AI doesn't just guess the answer. Instead, it follows a strict flow:
1. **The Tool Call:** The AI pauses, extracts the patient's name from the prompt, and triggers a custom Python tool I wrote.
2. **The Search:** My backend pulls every spoken word (audio transcripts) from every consultation that patient has ever had. 
3. **Context Extraction:** The system uses a FAISS Vector Database to search those massive transcripts and returns the 5 most relevant snippets.
4. **The Final Answer:** The AI reads those exact 5 snippets and streams an accurate summary back to the user interface.

**Why skip Manual Insights?**
A key design choice I made was forcing the AI to explicitly ignore the doctor's "Manual Insights" and only read the raw audio transcripts. If the Chat AI relied on summaries generated by another AI, any minor hallucination would compound in a game of "AI Telephone." Relying exclusively on raw transcripts ensures the system always works from the absolute ground truth.

---

## 2. Testing Methodology
To honestly evaluate the system without bias, I wrote an automated Python testing script using the **RAGAS framework**. RAGAS uses an "Evaluator LLM" (in my case, OpenAI's `GPT-4o`) to act as a strict, mathematical Judge. 

My script didn't use arbitrary mock data. It directly queried my SQLite Database to test 4 real patients across 20 distinct consultations. It generated questions asking for demographics, timeline summaries, and specific details from individual visits. I also injected 3 adversarial "trick" questions (like asking for a chocolate cake recipe or medication dosages) to test if my prompt guardrails actually worked.

---

## 3. The Model Benchmark: Llama 3.2 vs Llama 3.1
Because local execution speed is critical, I originally built the entire pipeline on `Llama 3.2 (3B)`. However, the RAGAS evaluation exposed severe limitations in using a small model for complex tool-calling.

### Trial 1: `Llama 3.2 (3B)`
* **Faithfulness (No Hallucinations):** `0.18`
* **Answer Relevancy (Stays on Topic):** `0.39`
* **Context Precision (Tool Accuracy):** `0.09`

The 3-Billion parameter model completely failed. Because it lacked advanced reasoning, it couldn't figure out how to correctly use my Python RAG tool. Instead of sending natural language queries to the database, it panicked and sent raw JSON dictionaries (`{"date_of_birth":"date"}`). The FAISS database couldn't read JSON, so it returned blank context windows. With no data to read, the AI simply hallucinated facts (crashing its Faithfulness score).

### Trial 2: `Llama 3.1 (8B)`
* **Faithfulness (No Hallucinations):** `0.75`
* **Answer Relevancy (Stays on Topic):** `0.68`
* **Context Precision (Tool Accuracy):** `0.39`

I upgraded the backend to `Llama 3.1 (8B)`, which Meta specifically trained for rigid tool-calling. The results were night and day. Llama 3.1 correctly stripped the complex JSON and sent perfect natural-language strings (e.g., `query="demographic background"`) into the FAISS tool. Because the database finally received coherent instructions, it pulled the correct transcript data. This instantly surged the system's Faithfulness score by over **400%**.

## 4. What I Had to Fix (Bugs & Optimizations)
Getting an 8-Billion parameter model to run fluidly on an **Intel Core Ultra 7 CPU** required a lot of trial and error. Here are the main bugs I had to patch:

### Bug 1: The Context Bloat Crash
* **What Happened:** In early testing, if a doctor chatted with the AI for too long, the local Llama model would completely crash.
* **The Fix:** Local open-weights models suffer massive performance drops if their memory window is overloaded. I hardcoded a memory constraint into the `/api/chat/sessions/` endpoint that forces the Agent to only "remember" the **last 6 messages** sent in a chat. This completely solved the crashing while maintaining conversational flow.

### Bug 2: Database Lag (FAISS Caching)
* **What Happened:** Heavy vectorization of audio transcripts usually takes several seconds to compute, causing massive typing lag in the chat UI.
* **The Fix:** I built a `patient_vectorstore_cache`. The system now only builds the heavy vector database the very first time a doctor asks about a patient. Any follow-up questions about that patient route instantly through the cache, dropping response times to milliseconds.

### Bug 3: Guardrail Failures
* **What Happened:** The AI originally tried to diagnose patients if pushed by the user. 
* **The Fix:** By locking down the `SYSTEM_PROMPT` and integrating the RAGAS edge-case testing, I proved that `Llama 3.1` now successfully detects trick questions and correctly refuses to give investment advice or prescribe medical dosages. 

---

## 5. Limitations & Future Work
While the system is now highly capable and deeply faithful to clinical facts (`0.75`), the **Context Precision score (0.39)** highlights the final remaining bottleneck: *Vector Retrieval.*

Currently, my pipeline uses a highly lightweight, open-source embedding model (`all-MiniLM-L6-v2`). While it runs instantly on my CPU, it struggles with deep semantic nuances when searching through thousands of medical transcript words. In the future, upgrading the architecture to a dedicated cloud Vector Database (such as Pinecone) and replacing the MiniLM embedder with a larger semantic model (like OpenAI's `text-embedding-3-small`) would easily push the Context Retrieval rates above `0.85`.
